# ZIP64 4GB 实测（2026-11-01）

## 背景

`kb_export(format="zip")` 原先用 JSZip 的 `generateNodeStream`。JSZip 3.10 只支持**读** ZIP64，
不支持**写** ZIP64；4GB 实测定位于此。

## 第一轮：JSZip（失败）

- 临时 KB：1 篇文档 + `sources/doc1.pdf`（4,400,000,000 字节稀疏文件，STORE）；
- 导出成功写出 4,400,002,933 字节，但中央目录把成员大小写成 **105,032,704**；
- `4,400,000,000 - 4,294,967,296 = 105,032,704`，即 32 位长度回绕，且没有 ZIP64 extra；
- 结论：JSZip 不能用于 >4GB 导出，`zip64: true` 选项不影响写出。

## 第二轮：yazl（通过）

- 依赖增加 `yazl@^3.3.1`；`exportZip` / `snapshotKb` / `exportVault` 全部改为 yazl 流式写入；
- 同一 4,400,000,000 字节 sparse PDF，`exportZip(includeSources=true)`：

```
zip_size       4,400,002,744
entries        6
source         file_size 4,400,000,000  compress_size 4,400,000,000  method 0 (STORE)
zip64_extra    true
```

- Python `zipfile` 读取通过；
- 内置 `openZipReader` 列出 6 个条目、source size 4,400,000,000，并读取 `manifest.json` / `kb.json` 正常；
- 结论：ZIP64 端到端可用（单成员 >4GB）。
- 测试产物 4.4GB 已删除。

## 代码

- `exportZip`：yazl `addFile`（流式、按大小自动 ZIP64）+ `end({forceZip64Format:true})`；
- `snapshotKb`、`exportVault` 同步切换；
- 移除无效的 JSZip `zip64` helper/test；
- 全量测试 **1287**（1283 通过、4 跳过，0 失败）。

## 备注

- 本次只验证“单成员 4.4GB + STORE”；多成员累加 >4GB、DEFLATE >4GB 未单独压测，但 yazl 的 ZIP64 是全包 EOCD + 超限成员统一处理，风险较低；
- 导入端 `zip-reader` 已支持 ZIP64；`kb_import_package` 对 >256MB 包自动走流式 reader。
