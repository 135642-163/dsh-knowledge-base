## 结论

- B 相对 A：Doc Recall 75.0% → 83.3%（8.3pp），MRR 0.466 → 0.608，p95 52ms → 53ms。
- B 相对 C（0.25 整句字面）：Doc Recall 3.3% → 83.3%，p95 28ms → 53ms。
- B 相对 C1（关键词 OR + 旧排序）：Doc Recall 1.7% → 83.3%。C/C1 的低分不是「rg 找不到字」，而是正则没有相关性排序；0.26 的机制回归（查询取条款原文开头）曾达到 95%，说明 rg 对「原样短语」有效、对人工问题无效。
- 门槛（0.27 spec §8.3）：B 相对 A Doc Recall +5pp 或 MRR +0.05 且 p95 < 200ms → 达标。
- D（纯 dense）相对 B：Doc Recall 83.3% → 60.8%，MRR 0.608 → 0.271，p95 7ms（dense 检索在 Python 侧计时）。
- E（RRF 混合）相对 B：Doc Recall 83.3% → 75.0%，Page Recall 78.3% → 75.0%，MRR 0.608 → 0.437，p95 62ms。
- 同义改写组：B 70.0% / D 40.0% / E 70.0% / F 70.0%（Doc Recall@10）——这是 0.29 的核心判据。
- F（文档级 RRF）相对 B：Doc Recall 83.3% → 79.2%，MRR 0.608 → 0.559，p95 59ms。
- 门槛（0.27 spec §8.5：Doc Recall +10pp、p95 < 500ms、索引 < 200MB/千篇）→ 未完全达标（体积约 321 MB/千篇）。
- 本轮只做离线评测，不改生产检索；是否把 embedding/RRF 接入 `kb_query` 与工作台留待 0.30，并按本报告的瓶颈（体积/延迟/中文同义词覆盖）决定量化与索引策略。

## 判读与 0.30 建议（人工分析）

### 先看结论

在 60 题人工问题上，**本轮没有一种 embedding/RRF 组合能超过现有的 FTS+boost（B）**：

| 组合 | Doc Recall@10 | MRR@10 | 相对 B |
|---|---|---|---|
| B（0.27 生产） | 83.3% | 0.608 | — |
| D 纯 dense（bge-small-zh） | 60.8% | 0.271 | −22.5pp / −0.337 |
| E 条款级 RRF | 75.0% | 0.437 | −8.3pp / −0.171 |
| F 文档级 RRF | 79.2% | 0.559 | −4.1pp / −0.049 |

同义改写组（10 题）Doc Recall：B 70.0% / D 40.0% / E 70.0% / F 70.0%——**没有提升**；
F 在改写组的 MRR 反而略高（0.358 vs 0.318），E 在该组的 Page Recall 更高（70% vs 50%），
但都不足以抵掉条款定位（B 100% vs F 95% / E 90%）与数值限值（B 93.3% vs F 86.7%）的损失。

### 为什么「语义检索」没有赢

1. **模型是最小档**：`bge-small-zh-v1.5` 只有 24M 参数（512 维）。观察 dense 分数分布可发现
   相关与不相关条款都挤在 0.63–0.72，区分度不足；典型坏例 Q52（灯光闪烁 → 闪变）的 top-5 全是
   「电能质量评估/电磁兼容」类近义文档，而不是 `GB/T 12326-2008`。同义词确实被召回了，但被近义
   文档淹没。
2. **语料里同族标准很多**：`GB/T 19963.1` / `.2` / `2011 非正式版`、`GB/T 15543-2008/1995`、
   `Q/GDW 10650.x` 等大量近重复文档。人标注的「唯一正确文档」在语义空间里并不唯一，小的 dense
   模型无法靠语义区分「现行版 vs 报批稿 vs 同族分册」——而这恰恰是标准问答最需要的区分。
3. **颗粒度**：D/F 把条款分 max-pool 成文档分，长表格/OCR 噪声条款会污染文档分；条款级 E 又把
   B 的强 top-1 稀释到 RRF 的中段（MRR 0.608 → 0.437）。
4. **指标偏置对词面有利**：60 题是「从条款原文反推问题」标注的（条款定位/数值题尤其如此），
   期望文档与条款文本共享大量词面；这让 BM25 占便宜。真正公平的语义测试只有同义改写 10 题，
   样本太小，且 bge-small 在这 10 题上没有优势。

### 值得在 0.30 之前补的实验

1. **文档级 embedding**（标题 + 标准号 + 标签 + 摘要 + 首段）：911 篇只需几秒，可作为「语义入口」
   与 B 的文档序做 RRF；比 15 万条款便宜两个数量级，也更接近「先找对标准、再找条款」的真实路径。
2. **更强的中文模型**：`jinaai/jina-embeddings-v2-base-zh`（768 维）或 bge-base-zh 级别；
   代价是 149k 条款嵌入从 27 分钟涨到 1–2 小时、索引体积翻倍（见下）。
3. **路由式混合**：只在 query 判定为「同义改写型」（无标准号、无高频条款术语）时启用 dense，
   其余查询保持 B；比全量 RRF 更可能只赚不亏。
4. **int8 量化**：当前条款级 float32 索引 292MB（321MB/千篇），超过 0.27 设计门槛
   （200MB/千篇）；int8 约 73MB（80MB/千篇）可过门槛，但要先证明质量不降。

### 决策

- **0.30 暂不把 embedding/RRF 接入生产检索**（`kb_query`、工作台 `/kb/api/search` 都不动）。
  当前证据下收益为负，而索引体积（321MB/千篇）与首建成本（27 分钟/911 篇）都超标。
- **保留本轮工具链**：`scripts/eval/{build-corpus.mjs, embed_corpus.py, dense_search.py, fusion.mjs}`
  + `scripts/eval-benchmark.mjs --vectors` 可用任意 fastembed 模型重跑，报告由脚本生成；
  `scripts/eval/fusion.mjs` 的 RRF 有单测（8 条），以后接入时不必重写。
- **判据更新建议**：0.27 spec §8.5 的「D 相对 C +10pp」应改成「相对 **B** 不下降，且同义改写组
  +10pp、体积 <200MB/千篇、p95 <200ms」——本报告的负结果就是按这个更严的判据得出的。
- 下一轮（若继续）先做「文档级 embedding + 路由式混合」，通过后再谈条款级与量化。

## 复现方式

```bash
# 1) 依赖（独立 venv，不进插件依赖；需要能访问 pypi/huggingface）
/opt/homebrew/bin/python3.12 -m venv /tmp/kb-eval312
/tmp/kb-eval312/bin/pip install fastembed           # onnxruntime + tokenizers + numpy

# 2) 语料（只读真实库索引）
node scripts/eval/build-corpus.mjs --out /tmp/kb-eval-029

# 3) 嵌入（92MB 模型；本机 92 条/秒，149519 条约 27 分钟）
/tmp/kb-eval312/bin/python scripts/eval/embed_corpus.py \
    --in /tmp/kb-eval-029 --out /tmp/kb-eval-029 --batch 128

# 4) dense 检索（numpy 暴力余弦，60 题约 0.3s）
/tmp/kb-eval312/bin/python scripts/eval/dense_search.py --in /tmp/kb-eval-029 --topk 200

# 5) 六变体对比并重写本报告
node scripts/eval-benchmark.mjs --vectors /tmp/kb-eval-029
```

`BAAI/bge-small-zh-v1.5`（dim 512，92MB），查询侧加中文检索指令
「为这个句子生成表示以用于检索相关文章：」；条款文本为「标准号+标题+条款号+小标题+正文」截断 480 字。
