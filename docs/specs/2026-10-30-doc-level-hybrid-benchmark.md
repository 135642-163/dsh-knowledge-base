## 结论

- B 相对 A：Doc Recall 71.3% → 78.8%（7.5pp），MRR 0.423 → 0.535，p95 58ms → 58ms。
- B 相对 C（0.25 整句字面）：Doc Recall 2.5% → 78.8%，p95 51ms → 58ms。
- B 相对 C1（关键词 OR + 旧排序）：Doc Recall 1.3% → 78.8%。C/C1 的低分不是「rg 找不到字」，而是正则没有相关性排序；0.26 的机制回归（查询取条款原文开头）曾达到 95%，说明 rg 对「原样短语」有效、对人工问题无效。
- 门槛（0.27 spec §8.3）：B 相对 A Doc Recall +5pp 或 MRR +0.05 且 p95 < 200ms → 达标。
- D（纯 dense）相对 B：Doc Recall 78.8% → 55.6%，MRR 0.535 → 0.231，p95 7ms（dense 检索在 Python 侧计时）。
- E（RRF 混合）相对 B：Doc Recall 78.8% → 71.3%，Page Recall 72.5% → 71.3%，MRR 0.535 → 0.383，p95 63ms。
- 同义改写组 Doc Recall@10：B 66.7% / D 40.0% / E 63.3% / F 76.7% / G 66.7% / H 80.0%——这是混合检索的核心判据。
- F（文档级 RRF）相对 B：Doc Recall 78.8% → 79.4%，MRR 0.535 → 0.490，p95 65ms。
- G（纯文档 dense，911 篇 / 1.9MB）：Doc Recall 65.0%，MRR 0.322，p95 2ms——文档级检索找不到页码，Page Recall 记 0。
- H（文档 RRF）相对 B：Doc Recall 78.8% → 84.4%，MRR 0.535 → 0.603；同义改写组 66.7% → 80.0%，同组 MRR 0.317 → 0.480。
- J（Oracle 路由上界）：Doc Recall 83.8%，MRR 0.596；这是「路由完全正确」时的上限，需要额外的意图判断才可能接近。
- 门槛（0.27 spec §8.5：Doc Recall +10pp、p95 < 500ms、索引 < 200MB/千篇）→ 未完全达标（体积约 321 MB/千篇）。
- 本轮只做离线评测，不改生产检索；是否把 embedding/RRF 接入 `kb_query` 与工作台留待 0.30，并按本报告的瓶颈（体积/延迟/中文同义词覆盖）决定量化与索引策略。

## 判读与 0.31 建议（人工分析）

### 三组数据一起看

**A. 20 条独立同义题**（先写问题、再按真实库定位期望，未照抄条款原文；单独跑）：

| 变体 | Doc Recall@10 | Page Recall@10 | MRR@10 |
|---|---|---|---|
| B FTS + boost | 65.0% | 55.0% | 0.317 |
| G 纯文档 dense | 65.0% | 0% | 0.275 |
| **H 文档 RRF** | **80.0%** | **65.0%** | **0.497** |

**B. 60 题主集**（与 0.27/0.29 可比）：

| 变体 | Doc Recall@10 | Page Recall@10 | MRR@10 |
|---|---|---|---|
| B FTS + boost | 83.3% | 78.3% | 0.608 |
| H 文档 RRF | **85.8%** | 77.5% | **0.638** |
| J Oracle 路由 | 85.0% | 78.3% | 0.630 |

**C. 合并 80 题**（本报告主表）：B 78.8% / 72.5% / 0.535 → H **84.4% / 74.4% / 0.603**。

### 结论

1. **文档级 embedding + RRF（H）是唯一全面不输 B、且在同义改写上显著更好的方案**：
   20 条独立同义题 +15.0pp、MRR +0.180；60 题主集 +2.5pp、MRR +0.030；80 题合并 +5.6pp、MRR +0.068。
   索引只要 **1.9MB**（911 篇 × 512 维 float32），查询嵌入约 **1.6ms**，本机首次建索引约 **11 秒**。
2. **条款级 dense（D/E/F）继续不推荐**：60 题上 60.8% / 75.0% / 79.2%，都低于 B；条款级索引 292MB
   且 27 分钟首建。
3. **H 的唯一短板是页内页码**：数值限值组 Page Recall 93.3% → 86.7%，因为文档级向量没有页码，
   dense 独有命中的文档无法定位到页。0.31 应做**两阶段**：先文档级融合，再在选中文档内用 FTS
   条款命中定位页码（`pageStart/pageEnd` 已有），即可把这条短板补回。
4. **暂时不需要按意图路由**（J ≤ H）：H 在条款定位（100%=100%）、跨文档（60→63.3%）、数值
   （93.3%=93.3%）都没有掉召回，反而多赚了改写与跨文档；唯一退步是条款定位的 MRR
   （0.875 → 0.772）——0.31 可用「词面强命中优先」规则（如标题命中且 ≥2 个检索词命中）把
   条款定位的排序锁回 B。

### 生产化选型（0.31）

- 运行时：`@huggingface/transformers`（transformers.js，ONNX/WASM，**无原生依赖**）加载
  `bge-small-zh-v1.5` ONNX（约 92MB 首次下载，可复用 `data/` 下的模型分发方式）；
- 索引：`<kb>/.index/doc-vectors.f32` + `manifestStamp` 增量刷新；911 篇首建约 11s，条目变动只重算改动文档；
- 接入点：`lib/search.js` 的 `rankResults` 之前做「B 文档序 + 文档 dense 序」RRF；README 与
  `/kb/api/status` 暴露 `semanticIndex: on/off`，默认关闭、可在设置里打开；
- 回退：模型不可用/索引缺失时完全走现有 B 路径（与 0.26 的 FTS 回退同款）；
- 延迟：查询嵌入 1.6ms + 911×512 余弦 <1ms，相对 60ms 的 FTS 可忽略。

### 本报告的局限
